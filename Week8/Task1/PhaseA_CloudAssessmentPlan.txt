4. CORE AWS CONCEPTS REVIEWED BEFORE EXECUTION
====================================================================
  - AWS Shared Responsibility Model — where AWS's responsibility ends
    and the customer's begins for each service used in this challenge
    (S3, IAM, EC2, EBS, Lambda, API Gateway).
  - Least privilege and the difference between identity-based and
    resource-based (bucket/trust) policies.
  - S3 permission layers: bucket policy, ACLs, Block Public Access, and
    the distinction between "static website hosting" (object GET) and
    "list bucket" (ListBucket API) — these are separate permissions and
    a bucket can allow one without the other.
  - The AWS "AuthenticatedUsers" grantee group refers to any AWS
    account holder globally, not members of a specific organization —
    a common and dangerous misunderstanding.
  - Temporary STS credentials: structure (AccessKeyId, SecretAccessKey,
    SessionToken), expiry, and why a session token must accompany the
    access key/secret pair when configuring a CLI profile.
  - EBS snapshot sharing and the risk of a snapshot being shared
    "public" vs. shared to a specific account ID.
  - EC2 Instance Metadata Service (IMDS): the difference between IMDSv1
    (no request signing, vulnerable to basic SSRF) and IMDSv2
    (session-oriented, PUT-based token requirement that mitigates most
    SSRF-to-metadata paths).
  - IAM policy evaluation logic: explicit deny > allow, and how
    Lambda/API Gateway resource policies interact with IAM identity
    policies.
